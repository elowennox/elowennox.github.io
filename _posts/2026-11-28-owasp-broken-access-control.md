## 1. OWASP Top 10이란?

OWASP(Open Worldwide Application Security Project)는 웹 애플리케이션 보안 향상을 목적으로 활동하는 비영리 단체이다.

OWASP에서는 웹 애플리케이션에서 중요하게 다뤄야 할 보안 위험 10가지를 선정하여 **OWASP Top 10**이라는 목록으로 발표하고 있다.

2025년 OWASP Top 10에서 가장 높은 순위를 차지한 항목은 **A01: Broken Access Control(접근 통제 실패)**이다. 2021년에 이어 2025년에도 1위를 유지하고 있다는 점에서 중요하게 살펴볼 필요가 있다.

이번 글에서는 Broken Access Control이 무엇인지, 어떤 상황에서 발생하는지, 이를 예방하기 위해서는 어떤 방법이 필요한지 알아보고자 한다.

## 2. Broken Access Control이란?

Broken Access Control은 접근 통제가 제대로 이루어지지 않아 사용자가 허용되지 않은 정보나 기능에 접근할 수 있는 보안 취약점이다.

접근 통제를 이해하려면 먼저 인증과 인가의 차이를 알아야 한다.

| 구분 | 인증(Authentication) | 인가(Authorization) |
|---|---|---|
| 의미 | 사용자가 누구인지 확인 | 사용자에게 어떤 권한이 있는지 확인 |
| 예시 | 아이디와 비밀번호로 로그인 | 일반 사용자의 관리자 페이지 접근 제한 |
| 목적 | 사용자 신원 확인 | 허용되지 않은 접근 차단 |

예를 들어 학교 홈페이지에 로그인하는 과정은 인증에 해당한다. 이후 학생이 자신의 성적만 조회할 수 있도록 제한하는 것은 인가에 해당한다.

즉, **인증은 사용자가 누구인지 확인하는 것이고, 인가는 그 사용자가 무엇을 할 수 있는지 결정하는 것이다.**

Broken Access Control은 이러한 인가 과정이 제대로 이루어지지 않을 때 발생한다.

## 3. Broken Access Control의 발생 원인

접근 통제 실패는 주로 서버에서 사용자의 권한을 충분히 확인하지 않을 때 발생한다.

대표적인 원인은 다음과 같다.

- **권한 검사 누락:** 사용자가 특정 기능을 실행할 권한이 있는지 확인하지 않는 경우
- **URL 및 매개변수 조작:** 주소나 요청값을 변경하여 다른 사용자의 정보에 접근할 수 있는 경우
- **관리자 페이지 접근 제한 미흡:** 일반 사용자가 관리자 전용 기능을 실행할 수 있는 경우
- **클라이언트 측 검증에 의존:** 브라우저에서만 접근을 제한하고 서버에서는 권한을 확인하지 않는 경우

이러한 문제가 발생하면 공격자가 다른 사용자의 개인정보를 조회하거나 수정할 수 있으며, 관리자 권한을 획득하거나 중요한 데이터를 삭제하는 등의 피해가 발생할 수 있다.

## 4. 대표적인 공격 유형

### 4.1. 수평적 권한 상승(Horizontal Privilege Escalation)

수평적 권한 상승은 동일한 권한 수준에 있는 다른 사용자의 정보나 기능에 접근하는 것을 의미한다.

예를 들어 사용자가 자신의 정보를 확인할 때 다음과 같은 주소를 사용한다고 가정해 보자.

```text
https://example.com/user/1001
```

이때 URL의 사용자 번호를 변경했을 때 다른 사용자의 정보가 조회된다면 접근 통제에 문제가 있는 것이다.

```text
https://example.com/user/1002
```

두 계정 모두 일반 사용자이지만, 자신의 정보가 아닌 다른 사람의 정보에 접근했다는 점에서 수평적 권한 상승에 해당한다.

### 4.2. 수직적 권한 상승(Vertical Privilege Escalation)

수직적 권한 상승은 일반 사용자가 관리자처럼 자신보다 높은 권한이 필요한 기능에 접근하는 것이다.

예를 들어 관리자만 접근할 수 있어야 하는 페이지가 다음과 같다고 가정해 보자.

```text
https://example.com/admin
```

서버에서 관리자 권한을 확인하지 않는다면 일반 사용자도 해당 페이지에 접근할 수 있다.

관리자 페이지에서 회원정보를 수정하거나 삭제할 수 있다면 피해는 더욱 커질 수 있다.

따라서 단순히 관리자 메뉴를 화면에서 숨기는 것이 아니라, 서버에서 실제 접근 권한을 확인해야 한다.

### 4.3. IDOR(Insecure Direct Object Reference)

IDOR는 사용자가 요청하는 데이터의 소유자나 접근 권한을 확인하지 않아 다른 사람의 정보에 접근할 수 있는 취약점이다.

예를 들어 온라인 쇼핑몰에서 주문 내역을 확인하는 주소가 다음과 같다고 가정해 보자.

```text
https://example.com/orders/1001
```

서버가 주문 번호만 확인하고 해당 주문이 로그인한 사용자의 것인지 확인하지 않는다면, 다른 주문 번호를 입력해 타인의 주문 내역에 접근할 수 있다.

이 경우 주문자의 이름, 주소, 구매 내역 등의 개인정보가 노출될 수 있다.

중요한 것은 **사용자가 요청한 데이터에 접근할 권한이 있는지 서버에서 확인해야 한다는 점**이다.

### 4.4. SSRF(Server-Side Request Forgery)

SSRF는 공격자가 서버를 이용하여 원래 접근할 수 없는 내부 시스템이나 외부 주소로 요청을 보내게 만드는 취약점이다.

예를 들어 웹사이트에 URL을 입력하면 해당 페이지의 정보를 가져오는 기능이 있다고 가정해 보자.

일반적인 사용자는 공개된 웹페이지의 주소를 입력하지만, 공격자는 서버 내부에서만 접근할 수 있는 주소를 입력할 수도 있다.

서버가 요청 대상에 대한 검증 없이 해당 주소에 접근한다면 내부 서비스나 중요 정보가 노출될 위험이 있다.

SSRF는 2021년 OWASP Top 10에서 별도의 항목(A10)이었지만, 2025년에는 Broken Access Control의 하위 유형으로 통합되었다.

이는 접근이 제한되어야 하는 서버 내부 자원에 접근할 수 있다는 점에서 접근 통제와 밀접한 관련이 있기 때문이다.

## 5. Broken Access Control 공격 예시

게시판에서 사용자가 자신의 게시글을 수정하는 상황을 생각해 보자.

정상적인 게시글 수정 과정은 다음과 같다.

1. 사용자가 로그인한다.
2. 수정하려는 게시글을 선택한다.
3. 서버에서 게시글 작성자와 로그인한 사용자가 동일한지 확인한다.
4. 권한이 확인되면 게시글 수정을 허용한다.

하지만 서버가 3번 과정을 생략한다면 어떻게 될까?

공격자가 다른 사람의 게시글 번호를 입력했을 때 해당 게시글까지 수정할 수 있는 문제가 발생할 수 있다.

즉, 단순히 로그인 여부만 확인하는 것으로는 충분하지 않다.

**로그인한 사용자에게 해당 게시글을 수정할 권한이 있는지까지 확인해야 한다.**

## 6. Broken Access Control 대응 방법

### 6.1. 서버에서 권한 검증하기

가장 중요한 대응 방법은 서버에서 사용자의 권한을 확인하는 것이다.

웹 브라우저에서 특정 버튼이나 메뉴를 숨기는 것만으로는 접근을 막을 수 없다. 사용자가 직접 HTTP 요청을 보내는 방식으로 기능에 접근할 수 있기 때문이다.

따라서 서버는 요청을 처리하기 전에 사용자의 권한을 검증해야 한다.

### 6.2. 최소 권한 원칙 적용하기

최소 권한 원칙(Principle of Least Privilege)은 사용자에게 필요한 최소한의 권한만 부여하는 것이다.

예를 들어 일반 사용자는 자신의 정보를 조회하고 수정할 수 있지만, 다른 사용자 계정을 삭제하거나 관리자 설정을 변경할 수는 없어야 한다.

필요하지 않은 권한까지 부여하면 계정이 탈취되었을 때 피해 범위가 커질 수 있다.

### 6.3. 기본적으로 접근 거부하기

**Deny by Default**는 명시적으로 허용된 접근을 제외하고 나머지 접근은 기본적으로 거부하는 방식이다.

모든 사용자의 접근을 먼저 허용한 뒤 특정 기능만 차단하는 것보다, 필요한 기능에 대해서만 접근을 허용하는 것이 안전하다.

### 6.4. 모든 요청에서 접근 권한 확인하기

한 번 로그인했다고 해서 이후 모든 요청을 허용해서는 안 된다.

게시글 조회, 수정, 삭제 등 각각의 요청에서 사용자가 해당 작업을 수행할 권한이 있는지 확인해야 한다.

특히 API를 통해 데이터를 수정하거나 삭제할 때도 동일한 권한 검사가 필요하다.

### 6.5. 접근 기록 관리 및 모니터링

접근이 거부된 기록을 저장하고 비정상적인 요청이 반복되는지 확인하는 것도 중요하다.

예를 들어 특정 사용자가 짧은 시간에 여러 계정의 정보를 반복적으로 조회하려고 한다면 의심스러운 행위로 판단할 수 있다.

이러한 기록을 분석하면 공격 시도를 조기에 발견하고 대응하는 데 도움이 된다.

### 6.6. SSRF에 대한 추가 대응

SSRF 취약점을 예방하기 위해서는 서버가 접근할 수 있는 요청 대상을 제한해야 한다.

- 서버에서 요청할 수 있는 URL과 호스트를 검증한다.
- 내부 네트워크나 중요 시스템으로의 불필요한 접근을 차단한다.
- 가능한 경우 허용된 목적지만 접근할 수 있도록 제한한다.
- 사용자 입력값을 검증하고 우회 가능성을 점검한다.

## 7. 정리 및 느낀 점

Broken Access Control은 사용자의 접근 권한을 제대로 확인하지 않아 발생하는 취약점이다.

이번에 공부하면서 로그인에 성공하는 것과 특정 기능을 사용할 권한이 있는 것은 서로 다르다는 점을 알게 되었다.

특히 URL의 숫자를 변경하는 것처럼 단순한 방법으로도 다른 사용자의 정보에 접근할 수 있다는 점이 인상적이었다. 복잡한 공격 기법을 사용하지 않더라도 서버의 권한 검증이 부족하면 심각한 보안 문제가 발생할 수 있다는 것을 알 수 있었다.

또한 접근 통제는 단순히 관리자 페이지를 숨기는 것이 아니라, 서버에서 각 요청의 권한을 확인하는 과정이 중요하다는 것을 이해하게 되었다.

결국 Broken Access Control을 예방하기 위해서는 **사용자가 누구인지 확인하는 것뿐만 아니라, 해당 사용자가 요청한 작업을 수행할 권한이 있는지 확인하는 것이 중요하다.**
