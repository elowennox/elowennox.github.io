## 1. OWASP Top 10이란?

OWASP(Open Worldwide Application Security Project)는 웹 애플리케이션을 비롯한 소프트웨어의 보안 향상을 목적으로 활동하는 비영리 단체이다.

OWASP에서는 웹 애플리케이션에서 중요하게 다뤄야 할 보안 위험 10가지를 선정하여 **OWASP Top 10**이라는 목록으로 발표하고 있다.

2025년 OWASP Top 10에서 가장 높은 순위를 차지한 항목은 **A01: Broken Access Control(접근 통제 실패)**이다. 2021년에 이어 2025년에도 1위를 유지하고 있다는 점에서 중요하게 살펴볼 필요가 있다.

이번 글에서는 Broken Access Control의 개념과 발생 원인, 관련 취약점 및 대응 방법에 대해 알아보고자 한다.

---

## 2. Broken Access Control이란?

### 2.1. Access Control(접근 통제)

접근 통제란 사용자가 특정 자원에 접근하거나 어떠한 행위를 수행하려 할 때 이를 허용할지 결정하는 것이다.

여기서 자원이란 파일, 데이터, 프로그램, 프로세스 등을 의미한다.

접근 통제와 관련된 기본적인 절차는 다음과 같다.

- **식별(Identification):** 사용자가 자신의 신원을 제시하는 과정
- **인증(Authentication):** 사용자가 제시한 신원이 실제로 맞는지 확인하는 과정
- **인가(Authorization):** 사용자가 특정 자원에 접근하거나 기능을 사용할 권한이 있는지 확인하는 과정

예를 들어 회사의 사내 업무 시스템에서 사원 번호를 입력하는 것은 식별, 비밀번호를 통해 본인임을 확인하는 것은 인증, 소속 부서와 직급에 따라 열람할 수 있는 업무 문서를 제한하는 것은 인가에 해당한다.

### 2.2. Authentication과 Authorization의 차이

| 구분 | 인증(Authentication) | 인가(Authorization) |
|---|---|---|
| 의미 | 사용자의 신원 확인 | 사용자의 접근 권한 확인 |
| 확인 대상 | 사용자가 누구인가? | 사용자가 무엇을 할 수 있는가? |
| 예시 | 아이디와 비밀번호로 로그인 | 일반 사용자의 관리자 페이지 접근 제한 |
| 목적 | 사용자의 신원 검증 | 허용되지 않은 접근 차단 |

인증에 성공했다고 해서 시스템의 모든 기능을 사용할 수 있는 것은 아니다.

예를 들어 회사의 사내 업무 시스템에 정상적으로 로그인한 직원이라도 인사팀의 급여 자료를 열람하거나 인사 담당자에게만 허용된 기능을 사용할 수 있어서는 안 된다.

따라서 보호된 자원에 접근할 때는 **Authentication뿐만 아니라 Authorization도 반드시 확인해야 한다.**

### 2.3. Broken Access Control

Broken Access Control은 접근 통제가 제대로 이루어지지 않아 사용자가 허용되지 않은 자원이나 기능에 접근할 수 있게 되는 보안 취약점이다.

대표적으로 적절한 인가 검증 없이 비즈니스 로직을 수행하는 경우에 발생할 수 있다.

여기서 비즈니스 로직(Business Logic)이란 게시글 수정, 회원정보 조회, 상품 결제 등 웹 애플리케이션이 실제로 제공하는 기능을 처리하는 로직을 의미한다.

접근 통제가 제대로 이루어지지 않으면 다음과 같은 문제가 발생할 수 있다.

- 다른 사용자의 계정 및 개인정보 접근
- 서버 내부의 중요 파일 열람
- 다른 사용자의 데이터 수정 및 삭제
- 관리자 전용 기능 실행
- 허용되지 않은 접근 권한 획득

## 3. Broken Access Control의 발생 원인

접근 통제 실패는 주로 서버에서 사용자의 권한을 충분히 확인하지 않을 때 발생한다.

대표적인 발생 원인은 다음과 같다.

- 인증 여부만 확인하고 인가 검사를 생략하는 경우
- URL이나 요청 매개변수를 변경했을 때 접근 권한을 검증하지 않는 경우
- 관리자 페이지에 대한 접근 제한이 제대로 이루어지지 않는 경우
- 브라우저에서만 접근을 제한하고 서버에서는 권한을 확인하지 않는 경우
- 사용자에게 필요 이상의 권한을 부여하는 경우

웹사이트뿐만 아니라 SSH, FTP와 같이 서버에 접근할 수 있는 서비스에서도 접근 통제가 제대로 이루어지지 않으면 보안 문제가 발생할 수 있다.

## 4. 대표적인 접근 통제 취약점

### 4.1. 수평적 권한 상승(Horizontal Privilege Escalation)

수평적 권한 상승은 자신과 동일한 권한 수준에 있는 다른 사용자의 정보나 기능에 접근하는 것을 의미한다.

예를 들어 호텔 예약 서비스에서 사용자가 자신의 객실 예약 정보를 조회한다고 가정해 보자.

```text
https://example.com/reservations/2021
```

이때 URL의 예약 번호를 다음과 같이 변경했다고 가정해 보자.

```text
https://example.com/reservations/2022
```

서버가 예약 번호만 확인하고 해당 예약이 현재 로그인한 사용자의 것인지 확인하지 않는다면 다른 고객의 예약 정보까지 조회할 수 있다.

이로 인해 다른 고객의 이름, 연락처, 숙박 일정 등의 개인정보가 노출될 수 있다.

두 사용자 모두 일반 고객이지만 자신에게 허용되지 않은 다른 고객의 정보에 접근했다는 점에서 수평적 권한 상승에 해당한다.

### 4.2. 수직적 권한 상승(Vertical Privilege Escalation)

수직적 권한 상승은 일반 사용자가 관리자처럼 자신보다 높은 권한이 필요한 기능에 접근하는 것을 의미한다.

예를 들어 관리자만 접근할 수 있어야 하는 페이지가 다음과 같다고 가정해 보자.

```text
https://example.com/admin
```

서버에서 관리자 권한을 확인하지 않는다면 일반 사용자도 해당 페이지에 접근할 수 있다.

관리자 페이지에서 회원정보를 수정하거나 삭제할 수 있다면 피해는 더욱 커질 수 있다.

단순히 일반 사용자의 화면에서 관리자 메뉴를 숨기는 것만으로는 이러한 문제를 방지할 수 없다.

서버에서 실제로 해당 사용자에게 관리자 권한이 있는지 확인해야 한다.

### 4.3. IDOR(Insecure Direct Object Reference)

IDOR는 사용자가 입력한 식별자를 통해 특정 객체에 접근할 때 해당 객체에 대한 접근 권한을 제대로 검증하지 않아 발생하는 취약점이다.

여기서 객체란 사용자 정보, 게시글, 예약 내역, 파일 등 시스템에서 관리하는 데이터를 의미한다.

예를 들어 게시판에서 게시글 번호를 기준으로 수정 기능을 제공한다고 가정해 보자.

정상적인 게시글 수정 과정은 다음과 같다.

1. 사용자가 로그인한다.
2. 수정하려는 게시글을 선택한다.
3. 서버에서 게시글 작성자와 현재 로그인한 사용자가 동일한지 확인한다.
4. 권한이 확인되면 게시글 수정을 허용한다.

하지만 서버가 3번 과정을 생략한다면 다른 사람의 게시글까지 수정할 수 있는 문제가 발생한다.

IDOR는 수평적 권한 상승으로 이어질 수 있는 대표적인 취약점이다.

중요한 것은 사용자가 로그인했는지뿐만 아니라 **요청한 객체에 접근할 권한이 있는지까지 확인해야 한다는 점**이다.

## 5. SSRF(Server-Side Request Forgery)

### 5.1. SSRF란?

SSRF(Server-Side Request Forgery)는 서버 측 요청 위조라는 의미로, 공격자가 서버를 이용하여 의도하지 않은 곳으로 요청을 보내도록 만드는 취약점이다.

일반적으로 외부 사용자는 서버 내부의 데이터베이스나 내부 서비스에 직접 접근할 수 없다. 하지만 웹 서버는 내부 시스템과 통신할 수 있는 경우가 있다.

SSRF는 이러한 서버의 접근 권한을 악용하는 것이다.

SSRF는 2021년 OWASP Top 10에서 A10이라는 독립적인 항목으로 분류되었지만, 2025년에는 A01 Broken Access Control에 통합되었다.

### 5.2. SSRF의 발생 원리

예를 들어 사용자가 URL을 입력하면 해당 웹페이지의 정보를 가져오는 서비스가 있다고 가정해 보자.

정상적인 요청 과정은 다음과 같다.

```text
사용자 → 웹 서버 → 외부 웹사이트
```

사용자가 입력한 URL에 대한 검증이 부족하다면 서버가 접근해서는 안 되는 내부 시스템으로 요청을 보내게 될 수 있다.

```text
공격자 → 웹 서버 → 접근이 제한된 내부 시스템
```

공격자가 내부 시스템에 직접 접근하는 것이 아니라 웹 서버를 중간에 이용하여 접근한다는 것이 SSRF의 특징이다.

따라서 서버가 사용자로부터 URL을 입력받아 처리하는 기능에서는 요청 대상에 대한 검증이 중요하다.

### 5.3. SSRF의 위험성

SSRF 취약점이 존재하면 다음과 같은 피해가 발생할 수 있다.

- 서버 내부 자원에 대한 비인가 접근
- API Key와 같은 중요 정보 유출
- 내부 네트워크 정보 노출
- 내부 서비스에 대한 허가되지 않은 요청
- 환경에 따라 추가적인 코드 실행이나 파일 변경 등의 피해

## 6. 서버 자원 접근과 관련된 추가 취약점

서버 자원에 대한 접근 제한이나 사용자 입력값에 대한 검증이 제대로 이루어지지 않으면 SSRF뿐만 아니라 경로 조작, 위험한 형식의 파일 업로드 등의 취약점도 발생할 수 있다.

각각의 취약점은 발생 원리에는 차이가 있지만, 공격자가 허용되지 않은 서버 자원에 접근하거나 이를 악용할 수 있다는 공통점이 있다.

### 6.1. 경로 조작(Path Traversal)

경로 조작은 사용자가 입력한 파일 이름이나 경로를 서버에서 제대로 검증하지 않아 허용되지 않은 파일이나 디렉터리에 접근할 수 있게 되는 취약점이다.

예를 들어 웹사이트에서 사용자가 업로드한 파일을 다운로드할 수 있는 기능을 제공한다고 가정해 보자.

정상적으로는 지정된 다운로드 폴더에 있는 파일에만 접근할 수 있어야 한다.

하지만 서버가 사용자가 입력한 파일 경로를 그대로 사용한다면 지정된 폴더의 범위를 벗어나 다른 파일에 접근할 수 있는 문제가 발생할 수 있다.

이러한 취약점이 발생하면 다음과 같은 피해가 발생할 수 있다.

- 서버의 중요 설정 파일 노출
- 허용되지 않은 파일 다운로드
- 서버 내부 정보 유출
- 파일 처리 기능에 따른 중요 파일 수정 및 삭제

따라서 파일 이름과 경로에 대한 입력값 검증이 필요하다.

### 6.2. 위험한 형식의 파일 업로드

위험한 형식의 파일 업로드는 사용자가 업로드하는 파일의 형식이나 내용을 제대로 검증하지 않을 때 발생하는 취약점이다.

예를 들어 프로필 사진을 등록하는 기능에서는 이미지 파일만 업로드할 수 있어야 한다.

하지만 서버가 파일의 형식과 내용을 확인하지 않는다면 서버에서 실행될 수 있는 스크립트 파일이 업로드될 가능성이 있다.

업로드된 파일이 서버에서 실행될 수 있는 환경이라면 공격자가 이를 악용하여 서버에 피해를 줄 수 있다.

대표적으로 웹 셸을 이용한 공격이 있다.

### 6.3. 웹 셸(Web Shell)

웹 셸은 웹 서버에서 실행되며 외부에서 서버에 명령을 전달하거나 서버를 원격으로 조작할 수 있게 하는 스크립트이다.

서버 환경에 따라 다음과 같은 확장자를 가진 스크립트 파일이 악용될 수 있다.

- `.php`
- `.jsp`
- `.asp`

이러한 확장자를 가진 파일 자체가 모두 악성 파일인 것은 아니다. 다만 악의적인 기능이 포함된 스크립트가 업로드되고 서버에서 실행된다면 보안 문제가 발생할 수 있다.

웹 셸이 실행될 경우 서버 프로세스의 권한 범위 내에서 다음과 같은 피해가 발생할 수 있다.

- 서버 내부 파일 조회
- 중요 정보 유출
- 파일 수정 및 삭제
- 허가되지 않은 명령 실행
- 추가적인 시스템 침해

따라서 파일 업로드 기능에서는 파일 형식뿐만 아니라 저장 위치와 실행 가능 여부까지 확인해야 한다.

## 7. Broken Access Control 및 관련 취약점 대응 방법

### 7.1. 인증 및 인가 검사 후 비즈니스 로직 수행

접근 통제 실패를 방지하기 위해서는 보호된 자원에 대해 Authentication과 Authorization을 모두 확인한 후 비즈니스 로직을 수행해야 한다.

예를 들어 계정 정보를 조회하는 기능이 있다고 가정해 보자.

**안전하지 않은 코드**

```cpp
if (CheckAuthentication()) {
    ShowAccountInfo();
}
```

위 코드는 사용자가 인증되었는지만 확인하고 계정 정보를 출력한다.

해당 계정 정보를 조회할 권한이 있는지는 확인하지 않기 때문에 다른 사용자의 정보에 접근할 가능성이 있다.

**안전한 코드의 기본 구조**

```cpp
if (CheckAuthentication()) {
    if (CheckAuthorization()) {
        ShowAccountInfo();
    }
    else {
        // 인가 오류 처리
    }
}
else {
    // 인증 오류 처리
}
```

위 코드는 인증에 성공한 이후 인가 검사를 추가로 수행하고, 두 조건을 모두 만족할 때만 계정 정보를 출력한다.

실제 구현에서는 인가 검사 시 현재 로그인한 사용자의 권한과 요청한 계정 정보의 소유 관계 등을 함께 확인해야 한다.

즉, **인증에 성공하였다는 이유만으로 비즈니스 로직을 수행해서는 안 되며, 반드시 해당 작업에 대한 권한을 확인해야 한다.**

### 7.2. 서버 측에서 권한 검증하기

사용자의 브라우저에서 버튼이나 메뉴를 숨기는 것만으로는 접근 통제를 보장할 수 없다.

브라우저에서 이루어지는 검증은 사용자가 변경하거나 우회할 가능성이 있기 때문이다.

따라서 사용자가 요청을 보낼 때마다 서버에서 해당 기능을 사용할 권한이 있는지 확인해야 한다.

조회뿐만 아니라 수정, 삭제 등의 작업에서도 동일하게 권한 검사가 이루어져야 한다.

### 7.3. 최소 권한 원칙 적용하기

최소 권한 원칙(Principle of Least Privilege)은 사용자에게 필요한 최소한의 권한만 부여하는 것이다.

예를 들어 일반 사용자가 자신의 정보를 조회하고 수정하는 기능만 필요하다면 다른 사용자 계정을 삭제하거나 관리자 설정을 변경할 권한까지 부여할 필요는 없다.

이를 통해 계정이 탈취되더라도 발생할 수 있는 피해의 범위를 줄일 수 있다.

### 7.4. 기본적으로 접근 거부하기

Deny by Default는 명시적으로 허용된 접근을 제외한 나머지 접근을 기본적으로 거부하는 방식이다.

모든 접근을 허용한 뒤 일부를 차단하는 것보다 필요한 접근만 허용하는 것이 안전하다.

접근 권한이 명확하게 확인되지 않는다면 해당 요청을 거부하도록 설계해야 한다.

### 7.5. 사용자 입력 최소화 및 검증

사용자로부터 불필요한 입력을 받지 않도록 설계하고, 입력받은 값은 서버에서 검증해야 한다.

사용자가 직접 입력할 수 있는 값의 범위가 넓을수록 예상하지 못한 값이 전달될 가능성도 높아지기 때문이다.

특히 파일 이름이나 경로를 입력받는 기능에서는 다음과 같은 특수문자가 포함되어 있는지 검사할 필요가 있다.

| 검사 대상 | 설명 |
|---|---|
| 슬래시(`/`), 역슬래시(`\`) | 파일 경로를 나타내는 문자 |
| 마침표(`.`) | 상대 경로 표현 등에 사용되는 문자 |
| 작은따옴표(`'`), 큰따옴표(`"`) | 문자열을 구분하는 문자 |
| 세미콜론(`;`), 콜론(`:`) | 명령이나 경로 등의 구분에 사용되는 문자 |
| `--`, `+`, 공백 | 입력값의 해석에 영향을 줄 수 있는 문자 |

입력값에 허용되지 않은 특수문자가 포함되어 있다면 해당 요청을 거부하거나 필요한 경우 안전하게 처리해야 한다.

다만 단순히 특수문자를 검사하고 제거하는 것만으로는 모든 공격을 방지할 수 없다.

경로 조작을 방지하려면 최종적으로 해석된 파일 경로가 허용된 디렉터리 내부에 존재하는지도 확인해야 한다.

### 7.6. 화이트리스트(Whitelist) 방식 적용

화이트리스트 방식은 미리 허용된 값이나 형식만 사용할 수 있도록 제한하는 방식이다.

반대로 블랙리스트(Blacklist) 방식은 위험하다고 판단한 값이나 형식만 차단하는 방식이다.

| 구분 | 화이트리스트 | 블랙리스트 |
|---|---|---|
| 기본 방식 | 허용된 것만 허용 | 금지된 것만 차단 |
| 파일 업로드 예시 | jpg, png 등만 허용 | php, jsp 등 차단 |
| 장점 | 예상하지 못한 형식도 기본적으로 차단 | 알려진 위험한 형식을 차단하기 쉬움 |
| 단점 | 허용할 형식을 미리 정의해야 함 | 목록에 없는 위험한 형식이 통과할 수 있음 |

파일 업로드 기능에서는 서비스에 필요한 확장자만 허용하는 화이트리스트 방식을 사용하는 것이 좋다.

또한 파일 확장자만으로 실제 파일 형식을 판단해서는 안 되므로 파일의 내용과 실제 형식도 함께 검증해야 한다.

### 7.7. 업로드 파일 이름 및 저장 경로 변경

사용자가 입력한 파일 이름과 경로를 그대로 사용하지 않고 서버에서 임의의 파일 이름을 생성하여 저장하는 방법이다.

이를 통해 파일 이름이나 경로를 악용하는 문제를 줄일 수 있다.

또한 업로드된 파일은 가능하면 웹에서 직접 접근할 수 없는 별도의 저장 공간에 보관하고, 파일을 조회할 때도 접근 권한을 확인해야 한다.

파일 이름이나 저장 경로를 변경하는 것만으로 접근 통제가 보장되는 것은 아니므로 별도의 권한 검증도 필요하다.

### 7.8. 업로드 파일 실행 제한

업로드된 파일이 서버에서 실행되지 않도록 설정해야 한다.

유닉스 환경에서는 불필요한 파일 실행 권한을 제거할 수 있으며, 웹 서버에서도 업로드 디렉터리 내의 스크립트 실행을 제한해야 한다.

운영체제의 실행 권한을 제거하더라도 웹 서버 설정에 따라 스크립트가 실행될 수 있으므로 두 가지를 함께 고려해야 한다.

이를 통해 악성 스크립트가 업로드되더라도 웹 셸로 악용될 가능성을 줄일 수 있다.

### 7.9. SSRF에 대한 대응

SSRF를 방지하기 위해서는 서버가 요청할 수 있는 목적지를 제한하고 사용자 입력값을 검증해야 한다.

대표적인 대응 방법은 다음과 같다.

- 사용자로부터 받는 URL 입력을 최소화한다.
- 입력받은 URL과 요청 대상에 대한 검증을 수행한다.
- 가능한 경우 화이트리스트 방식으로 허용된 목적지만 접근할 수 있도록 한다.
- 내부 네트워크 및 중요 시스템으로의 불필요한 접근을 제한한다.
- 다른 주소로 리다이렉트되는 경우에도 요청 대상에 대한 검증이 이루어지도록 한다.

사용자가 입력한 URL을 서버가 무조건 신뢰하지 않도록 설계하는 것이 중요하다.

### 7.10. 접근 기록 관리 및 모니터링

접근이 거부된 요청이나 비정상적인 접근 시도를 로그로 기록하고 지속적으로 확인해야 한다.

예를 들어 특정 사용자가 짧은 시간에 여러 계정의 정보에 반복적으로 접근하려는 경우 이를 의심스러운 행위로 판단할 수 있다.

이러한 기록을 분석하면 공격 시도를 조기에 발견하고 대응하는 데 도움이 된다.

## 8. 정리 및 느낀 점

Broken Access Control은 사용자의 접근 권한을 제대로 확인하지 않아 발생하는 보안 취약점이다.

이번에 공부하면서 인증에 성공하는 것과 특정 자원에 접근할 권한을 가지고 있는 것은 서로 다른 개념이라는 점을 알게 되었다.

특히 로그인 여부만 확인하고 인가 검사를 생략하면 다른 사용자의 개인정보가 유출되거나 관리자 기능이 악용될 수 있다는 점이 인상적이었다. URL에 있는 숫자를 변경하는 것처럼 단순한 방법으로도 보안 문제가 발생할 수 있다는 점에서 서버의 권한 검증이 중요하다고 생각하였다.

또한 SSRF, 경로 조작, 위험한 형식의 파일 업로드를 공부하면서 사용자가 입력한 값을 그대로 신뢰하는 것이 얼마나 위험한지 알 수 있었다.

이러한 취약점을 방지하기 위해서는 인증과 인가를 모두 확인한 후 비즈니스 로직을 수행해야 하며, 사용자 입력값에 대한 검증과 서버 자원에 대한 접근 제한도 함께 이루어져야 한다.

결국 웹 애플리케이션의 보안을 위해서는 사용자가 누구인지 확인하는 것뿐만 아니라 해당 사용자가 어떤 자원에 접근하고 어떤 행위를 수행할 수 있는지 지속적으로 확인하는 것이 중요하다고 생각한다.
